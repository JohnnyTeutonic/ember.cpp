# CUDA forward comparison - frozen workload

This is a separate CUDA counterpart to the completed CPU comparison. It does not alter or replay the CPU timing protocol. It measures one actual CUDA GPU with one host thread, FP32 weights/activations, TF32 disabled, eager HF attention, synthetic raw prompts16/128/512 and32 fixed output rows. The HF CUDA greedy continuation, including EOS, is frozen before native comparison.

Both timers start with CPU input IDs and end with a full CPU output-logit row: H2D input and D2H output transfers and synchronization are included. Token creation, tokenizer/sampler/argmax, JSON, row writing, model loading and startup are excluded. Native CPU wrappers, HF Python/cache dispatch and differing KV strategies remain included. These are runtime forward latencies, not isolated kernel or chat performance.

Before any timed shape, every full-vocabulary row and argmax must pass `max_abs_error / max(1,max_abs_HF_row) <= 1e-4`. Failed rows and HALTED markers remain; no tolerance change or prompt replacement. Each passed shape uses one warm request per engine followed by two ABBA cycles (four observations each). Completed trials are hash-chained, immutable on resume, and offline replayable. Native fallback is rejected; the binary must report actual GPU execution. Hardware, runtime, source/binary/weights and input hashes are recorded.

Candidate inputs are the exact existing F32 SmolLM2-135M and Gemma3-270M GGUFs used by the CPU comparison. Remote regeneration is acceptable only when the entire file SHA matches the canonical artifact; another revision, quantization or weights file is not a substitute. No model-quality or general engine-ranking claim follows from these synthetic measurements. Both models' results are recorded below: Smol on the RunPod image, and Gemma on Colab under [its amendment](gemma_colab_20261103/AMENDMENT.md).
The native loader now refuses any GGUF tensor type other than F32 (type 0), and records a complete named tensor/type/shape inventory digest, vocabulary and context in the protocol. Weight, executable, controller, native harness, interpreter sources and CMake hashes are checked before loading, after loading/gates, before and after each timed trial, and at completion (outside timers). Offline completion also requires the final integrity receipt and validates exact prompt formula, length, vocabulary width and continuation ranges. The hash chain detects accidental drift, not adversarial rewriting of an entire receipt. Historical CPU fallback proof refers only to its recorded source hash until a new build is recorded; it is not a current-source compile claim.


## Verified Smol-only L4 result, 30 October 2026

The canonical F32 GGUF regenerated byte for byte (SHA256 `a898c1208f35ae7c5456d8f19d868a7505b445916dddb1e906fa0296ffdda941`). All 96 paired full-vocabulary rows and greedy IDs passed the unchanged 1e-4 gate before timing. Two ABBA cycles supplied four observations per runtime at each shape, 24 immutable trials total. One host thread, context cap 1024, eager HF 4.57/Torch 2.4.1+cu124, actual L4 and TF32 off were independently checked.

| Prompt tokens | Ember prefill ms | HF prefill ms | Ember decode ms/token | HF decode ms/token | HF/Ember decode |
|---|---:|---:|---:|---:|---:|
| 16 | 5.181 | 26.506 | 3.278 | 12.941 | 3.948x |
| 128 | 8.416 | 24.941 | 3.292 | 12.751 | 3.873x |
| 512 | 24.700 | 25.459 | 3.364 | 12.778 | 3.799x |

These are synthetic runtime measurements, including dispatch/cache wrappers and synchronous CPU-ID to CPU-row transfers. They do not compare isolated kernels, compiled HF, chat latency or model quality. The 512-token prefill medians are close, with HF observations 20.34-28.97 ms; four observations do not establish a broad prefill advantage. The older portable/AVX2 CPU measurements remain separate and slower than HF on their measured workloads.

The local audit replayed every raw row, ID, trial hash chain and exact saved summary, then independently rehashed the existing canonical GGUF, archived CUDA executable and every interpreter/source file against the uploaded Git archive. The final ZIP is 39,988,204 bytes, SHA256 `e9eef4ca63beea4d42039ecbfe7db02dedd1b353e766a864a55d0c092dc5e4fb`; its single canonical home is recorded in [the final receipt](receipts/smol_v3_20261030_final.json). The public repository retains small receipts and replay code rather than another raw archive. Both attempt ledgers total about $0.34; their pods and volumes were removed.

Strict saved-summary replay uses CPython 3.11 arithmetic and NumPy 1.26.4, as on the pod. Host CPython 3.12 changes float summation, producing 18 last-bit summary differences (maximum 3.55e-15); [the diagnostic](receipts/smol_v3_python312_sum_diagnostic.json) preserves them. The unchanged archived analyzer passed exactly under local CPython 3.11.15/NumPy 1.26.4. No raw data, summary, rounding gate or timing criterion was edited. For an extracted artifact directory:

```bash
uv run --no-project --python 3.11 --with numpy==1.26.4 python out/controller.py --out out/smollm2-135m --analyze
```

The first Smol attempt's startup failures and HALTED marker remain in [its separate receipt](receipts/smol_20261030_operational_final.json). They occurred before model forwards or timing: the image's actual Torch patch version, a manual bootstrap missing CUDA PATH, and absent native GGUF lowering. The versioned repair [checks the complete launch contract](launch_contract_v3.py), explicitly enables the intended IR lowering/context cap and reuses the exact archived CUDA executable. It changes no numerical or throughput gate and repeats no scientific trial.

## Verified Gemma3-270M Colab L4 result, 3 November 2026

Run `g6-20261103` under [the Colab amendment](gemma_colab_20261103/AMENDMENT.md) (ember `9389eaa`; Codex methods review, 11 rounds). The run conditions:
- **Model file:** the canonical F32 GGUF regenerated byte for byte (SHA256 `0a174d42ccd7de15688e50dc044ea8006db31ee3bc6dc7e838f8a360ca46cdaa`).
- **Engine:** the frozen engine source, ember `5bfda893`, renamed `4d276ff9` by the 3 Nov history purge with an identical tree, built with CUDA 12.6.
- **Python and packages:** CPython 3.11.15 with the frozen top-level pins.
- **GPU settings:** one host thread, context cap 1024, actual L4, TF32 off.

All 96 paired full-vocabulary rows and greedy IDs passed the unchanged 1e-4 gate before timing. The worst relative errors were 1.6e-6 at 16 tokens, 2.9e-6 at 128 and 2.1e-6 at 512. Two ABBA cycles supplied four observations per runtime at each shape, 24 immutable trials in all.

| Prompt tokens | Ember prefill ms | HF prefill ms | Ember decode ms/token | HF decode ms/token | HF/Ember decode |
|---|---:|---:|---:|---:|---:|
| 16 | 7.023 | 34.116 | 5.645 | 31.180 | 5.523x |
| 128 | 20.057 | 34.157 | 5.968 | 31.380 | 5.258x |
| 512 | 174.021 | 34.252 | 6.980 | 31.291 | 4.483x |

The same limits apply as for Smol. In addition, at 512 prompt tokens ember's prefill is about 5x slower than HF's (all four observations 173-175 ms). That is a measured result of this workload; its cause has not been diagnosed here. Unlike Smol, this ran on Colab's image (Python 3.13 and CUDA 13 on the image, replaced as the amendment records), not the RunPod image, so it is not an environment-controlled comparison with the Smol result.

Before g6, five attempts stopped before the controller, each with its VM stopped and cleanup certified. Their causes were image changes, two build gaps and Colab CLI hangs, and the amendment's ledger records each. The local replay of g6 under CPython 3.11.15 and NumPy 1.26.4 reproduced the saved summary exactly, and every raw-row file matched the hash in its gate. The small receipts are in [`gemma_colab_20261103/receipts/g6-20261103/`](gemma_colab_20261103/receipts/g6-20261103/). The raw rows, the executable and the full output tree (about 200 MB) are in `C:/ml_artifacts/benchmarks/hf_cuda_gemma_colab_20261103/g6-20261103/`, pinned by `archive.sha256`. The replay:

```bash
uv run --no-project --python 3.11 --with numpy==1.26.4 python benchmark.py --out <archive>/run_g6-20261103/out/gemma3-270m --analyze
```
