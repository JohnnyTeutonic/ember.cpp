# Unicode NFC in ember's Qwen tokeniser, 25 Oct 2026

Qwen2.5's and Qwen3's `tokenizer.json` normalise with NFC before pre-tokenising. ember's Qwen
tokeniser (paperkiln's llama.cpp port, `llama3_tokenizer.h`) did not, so text written decomposed
(an "e" followed by U+0301, Korean as conjoining jamo) tokenised differently from HF. None of the
200 test prompts contains such text. This adds NFC for the Qwen path only (tokenizer.ggml.pre
"qwen2"); paperkiln's 16k Llama 3-scheme vocabulary, the 8k byte BPE and Gemma 3's SentencePiece are
untouched (LOCAL_LLM_STACK.md section 11, item 4.6).

## What changed

- `unicode_nfc.h`: NFC (UAX #15): full canonical decomposition, canonical ordering, canonical
  composition; Hangul syllables arithmetically. Text NFC leaves alone is returned as its own bytes.
- `unicode_nfc_tables.h`, generated by `tools/gen_nfc_tables.py` from Python's unicodedata
  (Python 3.12.3, Unicode 15.0.0): 814 combining classes, 2,060 decompositions, 940 composites,
  111 kB.
- `chat_tokenizer.h`: `QwenNfcTokenizer` wraps the port. Qwen's added tokens are all
  `"normalized": false`, so HF cuts the raw text at them first and normalises only the text between.
  The wrapper does the same: the port's cut (token types unknown, control and user-defined, longest
  first), NFC on each piece between, then the port on each piece. Text NFC leaves alone goes to the
  port whole, so its ids are the port's by construction. NFC could form an added token's text from
  other text only through the three ASCII characters NFC writes for a non-ASCII one (U+212A KELVIN SIGN
  -> "K", U+037E -> ";", U+1FEF -> "`"). A vocabulary whose added tokens hold one of them is refused at
  load; none of Qwen2.5's or Qwen3's do.

**HF's Unicode version.** HF tokenizers 0.22.1's NFC (the Rust crate unicode-normalization-alignments)
carries older tables than Python's. Probed over every code point, 108 combining marks added to Unicode
since then are inert there (class 0), and one composite is not formed (U+11938 DIVES AKURU VOWEL SIGN
O). The generator probes `tokenizers.normalizers.NFC` and drops exactly those, and lists them in the
header. `--python-only` writes Python's tables unfiltered. ember's ids must equal HF's, so the
committed tables are the filtered ones.

## Gates

**NFC itself** (`nfc_gate.py nfc`, `nfc_unit.json`): `tools/nfc_check` against HF's NFC normaliser,
string for string.

| Suite | Strings | NFC changes | ember = HF | ember = Python 15.0 |
|---|---:|---:|---:|---:|
| every code point alone (surrogates excepted) | 1,112,063 | 1,120 | 1,112,063 | 1,112,063 |
| every canonical decomposition (NFD), and each pair | 3,087 | 1,909 | 3,087 | 3,085 |
| every combining mark after a base, before and after a mark of every class | 304,260 | 131,746 | 304,260 | 281,881 |
| Hangul: every syllable decomposed, LV + T, L + V, L + mark + V | 22,743 | 22,344 | 22,743 | 22,743 |
| 200,000 seeded random strings of 1-8 code points | 200,000 | 124,972 | 200,000 | 198,215 |

ember equals HF on all 1,642,153 strings. Where it differs from Python, the string holds one of the
109 code points that HF's older tables do not know.

**Token ids** (`nfc_gate.py tokens`, `tokens_*.json`): `tools/llama3_vocab_check` against HF's
tokenizer on `nfc_set_v1.jsonl`, 337 strings that NFC changes (`make_nfc_set.py`; categories below).
Raw is `tok(text, add_special_tokens=False)`. Chat is the text as one user message under
`apply_chat_template(..., add_generation_prompt=True)`, for the texts that hold no added token (HF's
rendered text also equals ember's ChatML). The before-NFC column is the same tool built from ember
aa50a61.

The 12 strings the old build already got right are the added tokens followed by U+0338: HF leaves
the U+0338 alone because it sits in its own piece after the cut. NFC over the whole text would compose
the token's ">" with it.

**Unchanged.**
- The 22 Oct tokeniser receipts (`../thirdparty_2026-10-22/*/tokenizer_check.json`: 21 hard cases,
  200 prompts raw, 200 in the template) regenerate byte-identical with this build.
- `../chat_template_2026-10-24/rerun_all.sh` (run with 2 cores per job, the build from ember aa50a61
  plus this change): the G5 third-party receipt (Qwen2.5 409/409, Qwen3 909/909, Gemma 3 409/409),
  the in-place gate receipts (recursion, MoR, MoR refusals, attnres, state4) and all ten parity
  replays regenerate byte-identical. The WebAssembly receipts give the same replies, token counts
  and stop reasons (40/40, 60/60); only their `ms_per_reply` timing differs.
- Two receipts do not regenerate at aa50a61 with or without this change (the other ember agent's
  aa50a61 build gives the same two files): in `regress_bits.json`, IR_SPEC's load-time validation
  (f4516ff) now refuses `regress.py`'s hand-made `gpt2_tiny_recursion_0101` IR (block.repeat 4 with
  model.n_layers 2, weight_index on a gpt2 IR), and `state_tokens_gate_cpu.json`'s `vs_numpy_rel`
  values move (the ember side's checks all pass as before). Both are left as committed.
- The IR adapter self-test (`../ir_adapter_2026-10-25`) stays 119/119, its receipt byte-identical.

## Reproduce

`run.sh` (WSL, under the CPU budget): builds the tools, checks that the tables and the string set
regenerate byte-identical, and runs both gates. HF reference: tokenizers 0.22.1, transformers 4.57.0,
the tokenizer files beside the GGUFs in `C:/ml_artifacts/thirdparty/` (Qwen2.5-0.5B-Instruct f16,
Qwen3-0.6B Q8_0).
